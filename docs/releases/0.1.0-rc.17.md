# Music Index Studio 0.1.0-rc.17

This candidate makes a feed move safer. It also keeps a wrong computer clock from harming a feed in the index ([ADR 0126](../adr/0126-studio-refuses-a-bad-move-link.md), [ADR 0127](../adr/0127-a-changed-feed-gets-a-new-build-date.md) and [ADR 0128](../adr/0128-a-moved-feed-names-its-own-address.md)). It also corrects two faults of the desktop app on Linux. It comes after 0.1.0-rc.16.

## What changed

### A bad move link

- Studio now refuses a write with a loop or another bad link. This occurs before any file changes on a host. You cannot write over a refusal.
- Review shows "Studio refuses this write." It lists each address with its cause.
- When a repair exists, Review shows **Remove the Tag** or **Use the Public Address**. The repair changes the draft, and you review it before the write.
- A move now reads the feed on the new host before Studio writes the pointer file. A slow host gets 3 reads, with 10 seconds between them.
- If that read fails, the feed stays at its address. The new file stays on the new file host, and the next write replaces it.
- Review shows a notice when the self link of a feed names a different address. This notice does not stop the write.
- **Change:** a move to a private address now fails on the desktop too. A move to a host that cannot give the feed also fails until the host answers.

### A return to an earlier file host

- You can now move a feed back to a file host that it used before. The pointer file on that file host becomes the feed.
- Each move now adds the tag `itunes:new-feed-url` to the feed, with its new address. The diff shows this change. Do not remove this tag. The index can need it for a later return.
- Review warns you at each return. The index can wait before it follows a return, and the wait grows with each return.

### The build date

- When you change a feed, Studio now sets its `lastBuildDate`. The diff shows it as "Build date". You cannot edit this value.
- Studio uses the earliest of the computer clock and the time of a server. A clock that is ahead thus cannot put a date in the future.
- With no server answer, the feed keeps its date and the write continues.
- Review shows a notice when the computer clock is ahead, when no server answered, or when the feed already has a date in the future. No notice stops a write.
- **New requests:** Review of a changed feed asks two servers for the time: the musicindex API and the host of the feed. The answer stays in memory for 10 minutes.

### File drops

- With a mouse, each file field shows a drop hint. During a file drag, each target has a light outline.
- "Add tracks", "This Computer", "From MSP 2.0 backups" and "Import an account" now have a drop area.

### The desktop app on Linux

- A drop onto the window now gives Studio the file.
- Ctrl+Z now does an undo.

## What to test

The screenshots of each change passed. These steps need a real host, a real file manager or the real index.

### The desktop app on your Linux computer

1. Install the DEB or the RPM of your system, or run the AppImage, over 0.1.0-rc.16. Make sure that your collection stays.
2. Drag a music file from your file manager onto the file field of a track. Make sure that Studio receives the file.
3. Drag a file onto "Add tracks". Make sure that Studio receives the file.
4. Change a text field, then press Ctrl+Z. Make sure that the change goes back.

### A move on two real file hosts

5. Move a test feed from file host A to file host B. Select **Write to the File Host**.
6. Make sure that the feed is at the new address. Make sure that a second app reads the feed at that address.
7. In the diff, make sure that the new tag and the build date show.
8. Make a change, write the feed, and make sure that the index gives the new `last_build_date`.
9. On the file host, change `itunes:new-feed-url` in the feed file to an address that gives no feed.
10. In Studio, select **Read Again**, then open Review. Make sure that Studio refuses the write.
11. Select **Remove the Tag**. Make sure that the diff shows that change, then write the feed.

### The computer clock

12. On a computer where you can change the clock, set the clock one year ahead.
13. Make a change in a test feed, and open Review.
14. Make sure that the notice says that the clock is ahead. Make sure that the build date is the correct time.
15. Write the feed. Set the clock back, make a change and write again. Make sure that the index accepts each write.

### A roll back

16. Go back to an earlier version of a test feed, and write it. Make sure that the index gets that version.

## Known gaps

- The human test of a return waits for a release of Stophammer that holds its ADR 0083. A check in copies of both code sets passed. No deployed node ran it.
- A second return in a wait stays at the earlier address until the crawler reads the feed again. The check did not find how often this occurs.
- A cache with no `Age` header can give an early time. The notice about the clock can then be wrong. The build date stays safe.
- A server that does not answer can make Review wait, for a maximum of about 10 seconds.
- ADR 0126 condition 5 does not run, because Stophammer has no lookup of a feed by URL.
- ADR 0008 item 6 says that a move writes `podcast:previousUrl`, and Studio does not write it. This needs a decision.
- The macOS and Windows installers need a tester with that system.
- The human tests of Phase 12 (the server shell) and of tasks 065 to 084 stay open.
- The human tests of 0.1.0-rc.10 to 0.1.0-rc.16 stay open.
- The server part of the human test of task 086 stays open.
