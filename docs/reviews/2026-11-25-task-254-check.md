# The Operator Check Of Task 254 On 2026-11-25

This file records the findings of the operator check of [task 254](../tasks/studio-v1-task-254-the-sheets-of-a-catalog-change-review-and-drag-and-drop.md). The check uses the release binary of commit e663e59 with the real data of the operator. The main session corrects a finding after the check ends.

## Finding 1: a change of the role check boxes moves the page down

The operator changed the check boxes of the field "Role" on the page "HeyCitizen" (roles Artist, Label and Publisher, value "Custom"). Each change shows notices above the content. The notices push the content of the window down, so the check box below the pointer moves.

Cause: a role change calls `PUT /feeds/{id}/role` through `changeTwoDrafts` (`crates/api/ui/editor.js` near line 4620). The route changes the drafts of the releases of the page too. `ChangedNotices` then shows one notice for each changed release, above the content of the tab. On the page "HeyCitizen", four notices show.

Recommendation: defect. A notice after a change must not move the control that the user operates.

## Finding 2: the notices of a role change stay after the user puts the roles back

The operator put the check boxes back to their first values. The four notices "Studio also changed the draft of …" still show, and they have no close button. The head of the page says "No changes".

Cause: each role change replaces the notices with the `changed` list of its own call. The call that puts the roles back changes the same release drafts again, so it names the same releases. A notice has no close button.

Recommendation: defect. Not decided: if a release draft is equal to its written version after the change, its notice does not show. Each notice gets a close button.

## Finding 3: Undo does not undo a role change

Ctrl+Z and the Undo button do not undo a change of the role check boxes.

Cause: `setRoles` calls the route and records no step with `recordOperation`. A role change also changes the drafts of other feeds, so it is an operation, as the Catalog changes are.

Recommendation: defect. A role change records an operation whose `undo` sends the roles from before the change.

Corrections of findings 1 to 3 (main session, 2026-11-25):

- Finding 1: the notices of a role change show below the role field, so the check boxes do not move. A browser check gave the same position for the check box before and after a change.
- Finding 2: each notice has a close button. Open: a notice for a release draft that is equal to its written version still shows.
- Finding 3: a role change records an operation. Undo sends the roles from before the change, and Redo sends them again. A browser check gave both results.

## Finding 4: Releases shows above the Catalog

The operator asked why the row Releases shows above the heading "Catalog" in the left panel.

Cause: [ADR 0254](../adr/0254-the-catalog-is-a-tree-and-each-change-uses-music-words.md) item 2 gives this sequence: Releases, the tree, "No artist yet", "Other feeds". The code follows the decision.

Recommendation: a question for the operator, not a defect. A different sequence changes ADR 0254 item 2.

## Finding 5: the release list of a page and the row Releases

The operator finds that the row Releases of the left panel has low value. The release list of an artist page is more useful, but it has these faults:

- The select menu "Sort" is the wrong setting. The operator wants one standard sequence and a manual arrangement.
- The menu **⋯** of a release row gives only "Open", which is the same as a click on the row.
- A row shows no art and no release date.

The operator proposes: rows with art and release date, then no row Releases in the left panel.

Main session opinion: agree, with these points to decide in a mockup first. The sequence of the `podcast:remoteItem` elements in the artist feed can hold the manual arrangement, so the arrangement is in the feed file. The phone has no drag, so the menu **⋯** can give "Move up" and "Move down" and the changes of one release. Releases holds things that need a different place: the start page, the playlists, a search of each release, and "No artist yet".

Recommendation: an improvement that changes ADR 0254 item 2 and ADR 0072. Mockups first, then an ADR.

## Finding 6: a real mouse drag of a Catalog row does not start

Step 2 of the check: the operator held the mouse button on the row "HeyCitizen" and moved the mouse. The row did not move.

The main session did the same drag with `xdotool` in the release binary on a private Xvfb display, with a copy of the check data. A drag from the name of the row did nothing. A drag from the left edge of the row selected text. The screenshots of packet 254d used synthetic drag events in Chromium, so they did not find this defect. The desktop app turns off the Tauri file drop handler (`crates/desktop-app/src/main.rs` line 428), so that handler is not the cause.

Cause, proved with WebKitGTK on Xvfb: the drag start changed the page in the same task, and WebKitGTK then stops the drag. The log showed `dragstart` and then `dragend` at once. After the correction, the top area pushed the rows down by about 60 px during the drag, so the drop went to a different row.

Operator choice of 2026-11-25: a row that can move has a drag handle on its left side. The drag starts only from the handle. The handle shows that the row can move, and it prevents accidental drags. This rule applies to each app. The main session sent it to the orchestrator for the shared decision record.

Correction: the drag starts from the handle, and the drag state starts in the next task with `setTimeout`. The top area covers the heading "Catalog", so the rows do not move. In the release binary on Xvfb, an `xdotool` drag of the handle of "HeyCitizen" onto "Quiet Pine Records" gave the notice "HeyCitizen is now on Quiet Pine Records, not published. Not written yet."
